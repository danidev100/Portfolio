# «Pregúntale a mi IA» con Claude real: plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Que la Terminal conteste cualquier pregunta sobre Daniel con Claude Sonnet 5.5, en streaming, solo con su CV, iluminando los nodos que cita, y que vuelva al buscador local cuando Claude no esté disponible.

**Architecture:**

- `POST /api/ask` (Route Handler delgado) delega en `@/terminal/server`, que valida, limita por IP y por día, y convierte el stream de Claude en eventos `AskEvent` sobre SSE.
- El servidor implementa el mismo contrato `AskService` que el cliente: `createClaudeAskService` en el servidor y `createSseAskService` en el navegador. Un `AskService` compuesto decide entre Claude y el buscador local de V1.
- La base de conocimiento son bloques de texto atados a nodos del grafo, enviados como documento con citas; cada cita se traduce a nodos para `focus_nodes`.

**Tech Stack:** Next.js 16 (App Router, runtime Node) · React 19 · TypeScript strict · Zustand · `@anthropic-ai/sdk` · `zod` · Jest + Testing Library · Playwright + axe · pnpm · Render.

**Spec:** `docs/superpowers/specs/2026-10-20-ia-real-design.md`

## Global Constraints

- **Modelo:** `process.env.ANTHROPIC_MODEL ?? 'claude-sonnet-5-5'`. Key en `ANTHROPIC_API_KEY`, solo en el servidor.
- **Petición a Claude:** `client.beta.messages.stream` con `betas: ['server-side-fallback-2026-07-01']`, `fallbacks: 'default'`, `output_config: { effort: 'low' }`, `max_tokens: 1024`. Orden: `system` → documento con `cache_control: { type: 'ephemeral' }` → pregunta.
- **Pregunta:** recortada, de 1 a 500 caracteres. Cada pregunta va sola, sin historial.
- **Límites:** 10 preguntas por IP cada 10 minutos (`600_000` ms); tope blando global de 40 por día UTC. En memoria: una sola instancia en Render.
- **HTTP:** 400 entrada inválida · 429 límite · 503 Claude no disponible antes del primer evento (sin key, presupuesto agotado, red, 5xx). Ninguno lleva stream. Con stream: `200 text/event-stream`, un `data: <AskEvent JSON>\n\n` por evento.
- **Respuesta local:** si `/api/ask` no da stream, contesta `resolveAnswer` precedido de `(Modo sin conexión) `. Las preguntas sugeridas (también escritas a mano, comparadas como hace `resolveAnswer`) siempre van al guion local.
- **Textos fijos:** error a mitad de stream: «No pude responder a esa pregunta. Inténtalo de nuevo.» (el actual `SERVICE_FAILURE_MESSAGE`); rechazo de Claude sin texto: «No puedo responder a eso. Pregúntame por mi experiencia, mis proyectos o cómo trabajo.».
- **Temas delicados** (salario, disponibilidad, motivo de salida, ubicación, modalidad): nunca se responden; siempre se deriva a Contacto.
- **Fuente:** `CV_Daniel_Jaramillo_AI_Native.pdf`, con el LinkedIn `linkedin.com/in/daniel-jaramillo-bustamante`. Nada fuera del CV.
- **Nada de la IA en la carga inicial ni en el cliente:** el SDK solo se importa desde `src/terminal/server.ts`.
- **Los e2e y CI nunca llaman a Claude:** `e2e/support.ts` intercepta `/api/ask` por defecto.
- **Arquitectura:** dominio × tipo; dentro de `terminal`, rutas relativas; `src/app` solo importa `@/<dominio>` o `@/terminal/server`.
- **TypeScript:** `interface` para objetos, sin `any`, sin `as` injustificado, tipos de retorno explícitos en lo exportado.
- **Tests de servidor y SSE** con el docblock `/** @jest-environment node */`.
- **Commits:** Conventional Commits en inglés, terminados en `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Rama `feat/real-ai`.

## Review Focus

1. **El visitante pregunta otra cosa antes de que termine la respuesta:** la anterior se cancela y su llamada a Claude se aborta; no llegan tokens viejos. Test en Task 3 (el `signal` llega a `stream`), Task 4 (el handler pasa `request.signal` al servicio) y Task 5 (`createSseAskService` pasa `signal` a `fetch`).
2. **Claude falla a mitad de la respuesta:** el visitante conserva lo ya escrito y ve el mensaje de error, no una respuesta local mezclada. Test en Task 4 (error tras el primer evento → evento `error`) y Task 5 (el compuesto no cae a local tras el primer evento).
3. **Una cita que abarca varios bloques o repite nodos:** el foco acumula sin duplicados y en orden de aparición. Test en Task 3.
4. **`x-forwarded-for` con varias IPs o ausente:** se usa la primera; sin cabecera cuenta como `unknown`, y el límite sigue aplicando. Test en Task 4.
5. **Un evento SSE partido entre dos trozos de red o con JSON inválido:** se reconstruye; uno inválido termina en `error`, no en excepción sin controlar. Test en Task 2 y Task 5.

Traducción de eventos del stream:

| Evento de Claude                                                             | `AskEvent`                                                        |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `content_block_delta` con `text_delta`                                       | `token` con su texto                                              |
| `content_block_delta` con `citations_delta` de tipo `content_block_location` | `focus_nodes` con el conjunto acumulado, solo si añade algún nodo |
| `message_delta` con `stop_reason: 'refusal'` y sin tokens emitidos           | `error` con `REFUSAL_MESSAGE`                                     |
| fin del stream                                                               | `done`                                                            |
| thinking, `fallback` y el resto                                              | nada                                                              |

Un error lanzado **antes** del primer `AskEvent` se relanza como `AskUnavailableError`; después, se propaga tal cual.

`server.ts` empieza con `import 'server-only'` y crea **una** instancia de límites y servicio por proceso. Sin `ANTHROPIC_API_KEY`, el servicio es uno cuyo `ask` lanza `AskUnavailableError`. `route.ts` solo contiene `export { POST } from '@/terminal/server';` y `export const runtime = 'nodejs';`.

El handler, en orden:

1. Lee el JSON. Si falla, o `question` no cumple el esquema `zod` (string recortada, 1–500 caracteres), devuelve 400.
2. Si `limiter.tryConsume(clientId)` es falso, devuelve 429. `clientId` es el primer valor de `x-forwarded-for` recortado, o `unknown`.
3. Pide el primer evento a `service.ask(question, request.signal)`. Si lanza, devuelve 503.
4. Devuelve 200 con un `ReadableStream`: el primer evento y luego el resto, codificados. Un error a mitad de stream emite `error` con `SERVICE_FAILURE_MESSAGE` y cierra. Cabeceras: `content-type: text/event-stream`, `cache-control: no-cache, no-transform`, `x-accel-buffering: no`.
